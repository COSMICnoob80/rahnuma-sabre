## The 3 biggest blockers, ranked

### 1. First run can print "FIRE Achieved!" for a brand-new user — a false statement about their money
`src/screens/DashboardScreen.tsx:66`

```ts
const fire = calculateFIRE(monthlyExpenses || 1, currentCorpus, Math.max(currentSavings, 0), 10);
```

Nothing in the app forces expenses to be entered, so on a fresh install `monthlyExpenses === 0`. The `|| 1` guard
turns "no data" into "Rs 1 spent per month", i.e. annual expenses Rs 12, i.e. a FIRE target of **Rs 300**
(`calculators.ts:197`). Any corpus at or above Rs 300 then trips the early return at `calculators.ts:204`:
`yearsToFire: 0, progressPct: 100`.

Verified by executing the real module (not by reading it):

```
calculateFIRE(0 || 1, 250000, 0, 10) -> {"targetCorpus":300,"yearsToFire":0,"progressPct":100}
Dashboard verdict -> FIRE Achieved!
cash = Rs 500                        -> FIRE Achieved!   progressPct 100
```

So the very first card a stranger sees reads **`Rs 250,000 / Rs 300` · `100.0% of target` · `FIRE Achieved!`**. This is
the single most screenshot-worthy defect in the build, it is about money, and it is reachable in under a minute. It is a
correctness lie rather than a crash — but it is worse than a crash for a public post, because a crash reads as "bug"
and this reads as "doesn't understand finance".

The `|| 1` exists to dodge a divide-by-zero inside `calculateFIRE`; the honest fix is to render an explicit
"add your monthly expenses to see FIRE progress" state when there is no expense data — which is what the rest of the app
already does everywhere else (labelled gaps, never fabricated numbers).

### 2. A live provider key is baked into the shipped APK, and the README denies it
`assets/index.android.bundle` inside `rahnuma-sabre-r13-local-v13.apk`

Read out of the shipped binary (counted, value not printed): exactly **one** `gsk_…` key, 87 chars, in
`assets/index.android.bundle`. The same is true of r12; r7 (before the embedded-key feature) has one too, so this is not
new to r13 — it has been shipping for several rungs.

The mechanism is intentional and documented (`advisoryKey.ts:16`; `getConfiguredProviders()` appends embedded keys last
via `withEmbeddedFallback`, `secureStorage.ts:72`; the UI shows a "personal build key active" chip). The problem is not
that it exists — it is that:

1. `README.md:79` says **"nothing ships inside the binary, and there is no key baked into the repo"**. That sentence is
   false against the shipped artefact, and a public repo is exactly where someone checks it.
2. It is a free-tier key that anyone can extract from a 70 MB APK in one `unzip | grep`. It will be scraped, shared and
   burned, and the founder pays for it in rate-limit pain on the demo build.
3. It contradicts the pitch. "Everything stays on your phone" is about the user's data and remains true — but the
   sentence a reader remembers is the one about keys, and this is the one place the app is not what the README says.

The fix is a decision, not a build: either remove the embedded key (BYOK only, match the README) or keep it and state it
plainly in the README and the pre-launch checklist. The current state — ship it and deny it — is the only unacceptable
option.

### 3. Import says "positions saved" — and net worth never moves
`src/screens/SettingsScreen.tsx:242-259` writes to a table with no readers.

`getAssets()` is exported at `src/database/db.ts:107` and has **zero callers** anywhere in `src/` (grep: definition
only). Import nevertheless writes every non-cash row into `assets` and then tells the user
`"${assetRows.length} position(s) saved"` (`SettingsScreen.tsx:258`).

Meanwhile Dashboard net worth is `portfolioValue + cash + property` (`DashboardScreen.tsx:59`), where `cash` and
`property` are two scalar settings (`db.ts:204`, read at `DashboardScreen.tsx:40-43`). So:

- An FBR wealth line `Gold: 500000` → written to `assets` → invisible. Net worth unchanged.
- A bank CSV row → added to the `cash` setting, so cash does move — but the imported *positions* still do not.
- The "Import into local ledger" button therefore produces a confirmation message that is not true of any screen.

This is the same defect `SPINE.md:117` already recorded on 2026-10-25 ("imported `assets` rows are not yet part of
Dashboard net worth … a separate beat") and it was never closed. It is a data-truthfulness break on the one feature
whose entire job is data truth.

## Crash-class and correctness-class bugs with file:line

No hard crash was found by reading (every screen guards null prices, empty arrays and missing quotes; the font load
fails open, `fonts.ts:20`). What was found is one correctness-class defect that matters more than a crash:

| Class | Location | Defect |
|---|---|---|
| **Correctness (money)** | `src/screens/DashboardScreen.tsx:66` | `calculateFIRE(monthlyExpenses \|\| 1, …)` converts "no expense data" into a Rs 300 FIRE target and prints "FIRE Achieved!" for any corpus ≥ Rs 300. Reproduced live. |
| **Correctness (silent no-op)** | `src/screens/SettingsScreen.tsx:242-259` + `src/database/db.ts:107` | Import writes `assets` rows that no screen queries; the success Alert claims they were saved. |
| **Correctness (fell through)** | `src/screens/DashboardScreen.tsx:55` | Imported non-cash assets (gold, property, mutual funds) are excluded from `netWorth`; only the scalar `cash`/`property` settings count. |
| **Data (cosmetic)** | `src/screens/PortfolioScreen.tsx:176` | `(val / totalValue) * 100` is unguarded; safe today only because a holding cannot have zero value (quantity and price are validated `> 0`), so it renders `NaN%` only if that invariant is ever relaxed. |
| **UX (screenshot)** | `src/navigation/AppNavigator.tsx:124-136` | Nine bottom tabs. At 360 dp this is ~40 dp per tab; labels collide or truncate. |
| **PR (claim)** | `README.md:79` vs `assets/index.android.bundle` | "Nothing ships inside the binary" while a `gsk_` key does. |

## Community bar — what r/FIREPakistan actually rewards

Reddit blocks direct scraping from this host (login wall on `old.reddit.com`, 403 on `.json`, 504 on search), so this is
built from the subreddit's own stats page plus the tooling the community already recommends. The pattern is consistent.

1. **FIREPakistan rewards practical, specific answers over products.** 82k members; the dominant flair by a wide margin
   is **"Madad Me"** ("help me") at 53 posts, ahead of "Taaza Tareen" (10) and "Baaki Bakwaas" (5). The community is
   asking to be *helped with a decision*, not shown another tracker. Source:
   [GummySearch — r/FIREPakistan](https://gummysearch.com/r/FIREPakistan/).
2. **Specific local numbers earn credit; generic international tools get ignored.** The most-reviewed brands in the sub
   are local and concrete — Finqalab (4.1★ from 7 reviews) leads brokerage, HBL leads savings accounts. A PSX app is
   judged on whether it knows PSX mechanics, CGT, SECP and rupees. Rahnuma's CGT-by-acquisition-date and its
   never-advise law are exactly the kind of specificity this audience argues about.
3. **Privacy + free + open is a proven winner in adjacent investor communities.** Wealthfolio — an on-device,
   open-source investment tracker with no subscription — reached the front page of Hacker News and GitHub trending on
   precisely the three claims Rahnuma can also make ("simple", "private, data stays on your computer", "no subscription
   fees"). Source:
   [How I Built an Open Source App That Went Viral](https://dev.to/afadil/how-i-built-an-open-source-app-that-went-viral-160p).
   The lesson for r13: the privacy claim must *survive inspection*, which is why Blocker #2 matters far more here than
   it would in a normal product review.
4. **Competitors set a visible bar and they advertise it.** FolioSync, PSX Tracker, PSXTracker, Zarify and a Google-Sheets
   tracker all lead with live PSX prices, mutual-fund NAVs and FIFO/lot tracking. Rahnuma's differentiation (never
   advises, fully on-device, Urdu) is real and is *not* what those pages sell — but a reader will ask "does it track
   mutual funds?" and today the honest answer is no.

## VERDICT: **ONE MORE BEAT**

Not "POST NOW". The engineering underneath is good — enforced never-advise, honest freshness labelling, 235 green tests,
a self-healing council ladder, a real rollback ladder on GitHub. The problem is that all of that is one screen away from
a first-run experience that states something false about the user's retirement, a README that contradicts the shipped
binary, and a nine-tab bar that reads as unfinished. None of those are deep; all of them are visible on the first
screenshot.

Not "TWO MORE BEATS" either: the work below is small, scoped, and does not touch the architecture.

### Exact work list for the next beat

1. **Fix the FIRE first-run lie** — `DashboardScreen.tsx:66`. When there is no expense data, render an explicit
   "add your monthly expenses to see FIRE progress" state instead of `|| 1`. Add a unit test for
   `calculateFIRE(0, …)`-shaped input and a note on why zero expenses must never become a fabricated target.
2. **Resolve the embedded key, one way or the other** — either drop it and make the build BYOK-only, or keep it and
   correct `README.md:79` plus add a line to `docs/BETA-LAUNCH-POST.md`'s pre-launch checklist. Whichever way, the
   README and the APK must agree before anyone unzips the APK.
3. **Close the import loop or stop claiming it closed** — minimum: make `getAssets()` feed Dashboard net worth
   (gold/property/mutual-fund rows summed by kind), so the "position(s) saved" message becomes true. If that is too
   large for one beat, change the Alert to say exactly which screen the rows will appear on, and do not say "saved"
   until one exists.
4. **Cut the tab bar to five primary tabs** — Dashboard, Portfolio, Command, Budget, Settings — and move Directory,
   Costs, Calculators, Advisory behind a "More" entry or into Settings. Nine is the single most "unfinished" thing on
   screen.
5. **Add a first-run path** — one card on an empty Dashboard: "Add your first holding" → Portfolio's add form, and
   "Set your monthly income and expenses" → Budget. This is the onboarding gap that `SPINE.md:32` and `README.md:132`
   have both been carrying since October.
6. **Add at least a smoke render test for the Dashboard** — the suite is 235 pure-function tests and that is why
   Blocker #1 shipped green. Even one `react-test-renderer` pass over the empty-state Dashboard would have caught it.

Optional, if the beat has room: split the APK per ABI (arm64-only halves the download), and pick a license instead of
`TBD` so the repo is usable by anyone who wants to fork it.
